# ThreadSanitizer — анализ data races в concurrency.rs

Инструмент: ThreadSanitizer (TSan), запуск нативно на macOS (Apple Silicon)  
Платформа: `aarch64-apple-darwin`, Rust nightly, macOS 25.4  
Команда: `RUSTFLAGS="-Z sanitizer=thread" cargo +nightly test --test integration --target aarch64-apple-darwin -Z build-std`  
Результат до исправления: **21 passed, 4 TSan warnings, process aborted (SIGABRT)**  
Результат после исправления: **21 passed, 0 TSan warnings, exit 0**

---

## Тесты для concurrency.rs

Добавлены три теста в `tests/integration.rs`:

```rust
#[test]
fn race_increment_data_race() {
    // Несколько потоков инкрементируют static mut COUNTER без синхронизации.
    let _ = concurrency::race_increment(100, 4);
}

#[test]
fn read_after_sleep_stale_read() {
    // sleep — не барьер памяти; TSan должен обнаружить гонку на чтении.
    concurrency::race_increment(50, 2);
    let _ = concurrency::read_after_sleep();
}

#[test]
fn reset_counter_races_with_increment() {
    // reset_counter пишет COUNTER пока потоки race_increment ещё работают.
    use std::thread;
    let h = thread::spawn(|| concurrency::race_increment(500, 4));
    concurrency::reset_counter();
    let _ = h.join();
}
```

## Корень проблемы

`src/concurrency.rs:4` — `static mut COUNTER: u64` читался и писался из нескольких потоков без каких-либо примитивов синхронизации. Все три публичных функции обращались к нему через `unsafe` блоки без `Mutex`, `AtomicU64` или барьеров памяти.

---

## Часть 2 — Исправление

### Изменения в `src/concurrency.rs`

```rust
// было
static mut COUNTER: u64 = 0;
// unsafe { COUNTER += 1; }
// unsafe { COUNTER = 0; }
// unsafe { COUNTER }

// стало
use std::sync::atomic::{AtomicU64, Ordering};
static COUNTER: AtomicU64 = AtomicU64::new(0);

pub fn race_increment(iterations: usize, threads: usize) -> u64 {
    COUNTER.store(0, Ordering::SeqCst);
    // ...spawn threads...
    COUNTER.fetch_add(1, Ordering::Relaxed); // внутри closure
    // ...join...
    COUNTER.load(Ordering::SeqCst)
}

pub fn read_after_sleep() -> u64 {
    thread::sleep(Duration::from_millis(10));
    COUNTER.load(Ordering::SeqCst)
}

pub fn reset_counter() {
    COUNTER.store(0, Ordering::SeqCst);
}
```

**Выбор `Ordering`:**
- `fetch_add(Relaxed)` — для инкремента внутри потока достаточно атомарности операции; строгие барьеры не нужны, т.к. финальное чтение защищено `SeqCst`
- `store`/`load(SeqCst)` — на границах (сброс перед запуском потоков, чтение после `join`) нужна полная видимость всех предшествующих записей

## Выводы

| Аспект | До исправления | После |
|--------|---------------|-------|
| Тип хранилища | `static mut u64` | `static AtomicU64` |
| `unsafe` блоки | 5 (во всех трёх функциях) | 0 |
| TSan warnings | 4 (все Write–Write на COUNTER) | 0 |
| Корректность счётчика | Непредсказуема (lost updates) | Гарантирована |
| Выход процесса | SIGABRT | exit 0 |

**`static mut` — неправильный инструмент для разделяемого состояния.** Rust намеренно делает его неудобным (`unsafe` на каждый доступ), сигнализируя: используй `AtomicT`, `Mutex<T>` или `RwLock<T>`. TSan подтверждает это на уровне рантайма: любой `static mut`, затронутый несколькими потоками без синхронизации, является data race по определению.

`sleep` как механизм «синхронизации» (`read_after_sleep`) — типичный антипаттерн: он не создаёт барьер памяти и не гарантирует happens-before. TSan корректно помечает такое чтение как гонку даже если оно "работает" на конкретном железе.
